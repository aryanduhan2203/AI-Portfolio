## Project: QuickDine
GitHub: https://github.com/aryanduhan2203/QuickDine
Live site: http://15.206.36.95
A full-stack food delivery platform with three separate logins: customer, shop owner, and driver.
- Stack: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS, Supabase (Postgres and real-time), Razorpay, OneSignal, Docker, AWS.
- Customers: restaurant search, cart with GST and delivery fee, checkout with Razorpay (cards, UPI, wallets, cash on delivery), and push notifications for every order status change.
- Store owners: a dashboard with order lanes (New, Preparing, Ready, Completed), menu editing, availability controls, daily analytics, performance insights, and replies to reviews.
- Drivers: online/offline duty toggle, a live feed of orders that are being prepared, one-click order claiming with checks so an order cannot be claimed twice, delivery progress updates, and a daily earnings tracker.
- Payments: the server creates the Razorpay order, verifies the payment signature, and also handles Razorpay webhooks. Amounts are converted to integer paise with Math.round to avoid Razorpay's "amount must be an integer" error. The checkout modal resets cleanly if the customer closes it midway.
- Order flow: a new order is placed silently, and drivers and the customer are notified only after the restaurant accepts it (Preparing), then again at Ready, In Transit and Delivered.
- Order processing: after a payment is verified, the order is sent to an AWS SQS queue (ORDER_CONFIRMED event). A dead-letter queue catches messages that fail 3 times.
- Real-time sync: Supabase real-time subscriptions keep the dashboards live, with a 15-second polling fallback.
- Notifications: OneSignal push notifications are triggered from Next.js API routes when an order status changes, and user identities are synced with the Supabase session.
- Cloud and DevOps: I went from zero DevOps knowledge to a full cloud deployment. A multi-stage Docker build (Node 20 Alpine) runs on an AWS EC2 instance (Ubuntu, ap-south-1) behind an Nginx reverse proxy with an Elastic IP, and the container restarts automatically.
- Storage: images live in a private S3 bucket and are served through short-lived presigned URLs generated by a Lambda function behind API Gateway.
- Analytics: Google Analytics is integrated.

## Project: Predictive Maintenance for Military Equipment
GitHub: https://github.com/aryanduhan2203/Predictive-Maintenance-for-Military-Equipment
A machine learning notebook that predicts the Remaining Useful Life (RUL) of jet engines from sensor data, built on the CMAPSS FD001 turbofan dataset (100 engines, about 20,600 rows, 21 sensors and 3 operating settings).
- Approach: compute RUL per engine as the last cycle minus the current cycle, run exploratory analysis (degradation curves, RUL distribution, correlation heatmap), drop near-constant sensors, pick 10 informative sensors plus operating settings, scale the features, and train a Random Forest regressor.
- Results: R² of 0.70, MAE of about 26.7 cycles and RMSE of about 36.5 on a 10% hold-out test set.
- Diagnostics: residual plot, actual vs predicted plot, and residual distribution.
- Built with Python, pandas, NumPy, scikit-learn, Matplotlib and Seaborn.

## Project: Project Management Backend
GitHub: https://github.com/aryanduhan2203/Projevx
A REST API for collaborative project management, with user accounts and role-based access control. I built it solo.
- Stack: Node.js, Express, MongoDB (Mongoose), JWT, bcrypt, Nodemailer with Mailgen, express-validator.
- Authentication: registration with email verification, login and logout, JWT access tokens with a refresh-token flow, forgot and reset password, change password, and resending the verification email.
- Roles and permissions: there are three roles (admin, project admin, member), and they are per project, not global. Whoever creates a project automatically becomes its admin. A permission middleware looks up the caller's membership for that project and returns 403 if they are not a member or their role is not allowed for that action.
- What each role can do today: any member of a project (admin, project admin or member) can view the project and its member list. Only the admin can update or delete the project, add members, change member roles and remove members. Any logged-in user can create a project and list their own projects.
- Project admin role: it exists in the data model and is meant for managing tasks and content, but because the task and notes endpoints are not built yet, it currently has the same access as a member.
- Projects: create, list, view, update and delete projects, plus adding members, listing them, changing their roles, and removing them.
- Structure: versioned API under /api/v1, a health-check endpoint, validators, and shared utilities for error handling and API responses.
- Not built yet: the task, subtask and notes endpoints and file attachments. Their data models exist, but the routes and controllers are still to do.
